Production flow -- systemic, no duplicate target-validation cache
1. advance_content_drag(dt) updates the existing typed pointer/capture and performs
   edge scroll only. It does not query/validate an authoring target or produce ops.
   Native motion uses dt0; the held frame uses nonzero dt once, as before.
2. Dispatch and layout recycle/position the bounded rows normally.
3. The final main render calls settle_content_feedback after the late diagnostic
   and Game-preview rebuild sites. It uses the existing shared content target
   resolver once and repaints the matching ghost/caret. It does not scroll again.
   It handles all payloads, not collections alone. A validation error becomes a
   rejected preview plus the existing diagnostic path, not a stale accepted drop.
4. The final floating frame wrapper does frame + settle with the same enter/leave
   and returning-surface ownership as existing frame_surface. No additional
   surface-ID clone is introduced compared with that existing wrapper.
5. Native material picking caches the current borrowed draw's subtree-local slot
   without requiring pre-layout rejection feedback. Import/lock/target validation
   happens in the same common post-layout/release resolver. Native re-picks clear
   old surface/material contacts first, including a miss at the same pointer.
6. content_drag_over remains a standalone/release compatibility wrapper. The
   finish path still calls it at dt0 and resolves the target afresh before the
   existing typed command-producing-ops commit. No authoring validation is skipped.

Why refresh does not cause an incorrect release retarget
The displayed target is resolved from the captured pointer on its owning surface
against the current row bindings, after layout. The source ItemKey remains in the
original DragSession. In the controlled regression, scrolling moves the pointer
from after item100 to before item101: the resolver now advertises that current row
and current caret, which represent the SAME insertion slot. Release at unchanged
pointer/layout revalidates that slot at dt0. If model/layout really changed, fresh
release validation rejects or resolves the actual new target; no stale target is
silently committed. Native item100 proof waits in the neutral band so its literal
after-item100 target remains stable across the real pointer move and release.
