ARA · DECISION D29 / EXPERIMENT E7 · 27 OCTOBER 2026

Vendor reconstruction:
licences and integration

Integrate optional providers behind Ara’s own temporal contract. Keep Ara TAAU as the default, reference and fallback. A public engine can support these SDKs, but proprietary feature runtimes retain their own terms.

Proceed: FSR 3.1 and MetalFX; DLSS after owner acceptance of NVIDIA’s obligations; XeSS Super Resolution on Windows/Vulkan. Sequence later: Ray Reconstruction when its signal inputs exist; XeSS frame generation when a supported native API exists; FSR 4 Vulkan after AMD publishes SDK 2.4.

New since the fidelity report: AMD’s 20 October announcement promises Vulkan upscaling and ML frame generation in forthcoming SDK 2.4. SDK 2.3 remains the latest public release checked today. “DX12-only” still describes the released FSR 4 SDK, but now needs this announced-successor qualification. [F5] [F7]

Owner action: accept NVIDIA’s runtime terms, release notification and branding obligations before adoption; personally approve any new SDK agreement or programme enrolment. This review does not accept agreements, register accounts or notify vendors.

4. Renderer and presentation inputs

Ara design: one per-view descriptor carries input/output extents, frame ID, jitter, history reset reason, exposure convention, motion-vector scale/direction and depth convention. Adapters translate these to SDK conventions with explicit layouts and lifetimes. Reset for cuts, resize, provider switches and origin rebases. Provider state belongs to presentation, never deterministic simulation.

6. Optional setup, packaging and notices

Proposed, not implemented: a small ara-reconstruct module/crate with adapter modules and a CPU-only capability/status API. Native handles/unsafe calls stay behind GPU-backend boundaries. No general plugin platform is needed. Steam Audio provides the precedent: explicit setup, pinned SHA-256, safe extraction, trusted absolute paths, preserved notices and no Cargo-triggered download. [A3]

Where files live and how they arrive

  1. Provide an explicit tools/fetch_reconstruction_runtime.ps1 and non-Windows counterpart. A future ara setup reconstruction --provider dlss is a proposed CLI, not an existing command. Present the exact licence and release before agreement-dependent acquisition; store acceptance version/hash locally only after owner acceptance.
  2. Stage into ignored crates/ara-reconstruct/runtime/<provider>/<version>/<target>/, with original metadata, checksums and licenses/. Tests use fresh directories under target/, never the real user profile. A shared cache can follow later as an explicit option.
  3. Public repo may contain Ara adapters, legally redistributable headers/bindings, source provenance, official URLs/checksums, version rules, notices templates and missing-runtime fixtures. Exclude proprietary SDK headers/archives, feature binaries, developer tools, credentials and acceptance receipts. MIT FSR source/shaders may be committed with notices, while its provider stays optional at runtime.
  4. Fresh-clone Cargo check/test must compile without downloaded SDKs. MIT Streamline bridge, Intel C declarations and Apple Rust bindings fit this rule. FSR shader/provider preparation is an explicit maintainer/setup task; consumer Cargo must not invoke upstream CMake/Python or download a compiler. Use the fixed supported tools or a provenance-tracked optional provider kit. A direct-NGX bridge needing restricted headers is prepared only in that licensed kit, not by normal workspace builds.
  5. Load validated absolute paths; check checksum/signature where available, ABI, architecture and exports. Avoid current-directory/PATH discovery. Library handles outlive all provider objects and in-flight GPU work. Never hot-swap an active provider.
  6. Export only selected production files with ThirdPartyLicenses/. Preserve app-root placement where required, and give Streamline explicit plugin paths. Incorporate NVIDIA into a functional game/application rather than redistribute its SDK standalone. Setup downloads directly from official vendor URLs instead of mirroring proprietary SDK bundles.

7. Implementation order for E7

This is build order, not a feature cut. Unreleased APIs remain explicit follow-up work. Re-estimate the original 2–3 weeks after legal/setup and presentation dependencies are resolved. [A2]

  1. E7.0 — Temporal and capability contract. Confirm per-view motion/depth/jitter/exposure/reset conventions, TAAU reference and CPU-only status. Separate scene/UI and presentation ownership. Add missing-provider fixtures without automatic download.
  2. E7.1 — Setup and export seam. Freeze versions/licences/manifests and notices. Resolve NVIDIA sign-off while MIT FSR and system MetalFX work can proceed. Verify no extra SDK/tool in fresh-clone checks. Include notice collection in export before declaring an adapter shippable.
  3. E7.2 — Super resolution. On 4070 SUPER, Streamline DLSS SR first after sign-off; FSR 3.1 Vulkan, MetalFX temporal on M5, then XeSS SR Windows/Vulkan. Native Linux DLSS follows with the licensed NGX kit; Linux FSR uses the prepared provider. No backend port just for XeSS.
  4. E7.3 — Frame-generation foundation. One pacing/presentation owner, HUD-less scene, separate alpha UI and retained resources. Validate resize, minimize/restore, device loss, HDR, multiple editor windows, capture and FG-off recovery before enabling FG.
  5. E7.4 — Available FG providers. DLSS ordinary FG plus Reflex on RTX 40; FSR 3.1 cross-vendor Vulkan; MetalFX interpolation on macOS 26+. Expose queried modes only. Native NGX Linux FG is separately qualified.
  6. E7.5 — Ray reconstruction. DLSS RR when actual noisy ray inputs, material attributes and reflection-motion data exist; compare with current denoising. MetalFX denoised scaling is a separate optional experiment under the same rule. Deterministic hybrid lighting does not need RR merely because the SDK offers it.
  7. E7.6 — Successor review. Reopen this review for released FSR SDK 2.4 Vulkan SR/ML FG or future Intel Vulkan FG/XeLL. Verify licence diff, native OS artifacts, exact requirements, update/network controls and pacing/UI contract before enabling.
  8. E7.7 — D29 evidence and release. Report real-frame GPU/CPU time separately from presented rate; generated frames never count toward D26/D27 budgets. Compare DLSS 0.5 scale against TAAU 0.67 for region FLIP/stability; target 4K High p95−25% at equal quality. Qualify doubled presented rate with at most one frame of added latency through a defined latency measurement, not FPS inference. Keep fallback quality first-class. [A1] [A2]

Future gates: focused changed-crate check/clippy/tests and diagnostic coverage; no-runtime clean environment; native feature queries and recovery; per-platform quality/stability/pacing/latency evidence. Serialize future GPU measurements through ara-dev gpu. No such build or measurement was run for this report.
