# TL;DR

- **Build on selected Bevy crates; do not fork Bevy.** Start with `bevy_ecs`, `bevy_app`, `bevy_reflect`, tasks/math and selectively assets. Own snengine's persistent documents, commands, renderer and editor.
- **Bevy is now 0.20.0**, released October 8, 2026. BSN composition shipped, but `.bsn` asset files and the complete upstream editor remain work in progress. Fyrox has shipped its native editor and 1.0 release.
- **wgpu 30.0.1 is substantially more capable than “just WebGPU.”** Native bindless features, experimental mesh shaders and ray queries exist. Explicit multi-queue scheduling and complete ray-tracing pipeline parity remain reasons to retain a raw-backend escape route.
- **Use Slang for flagship native shaders**, initially through an offline compiler process. Use WGSL/WESL for the portable subset. Neither Rust nor Slang removes platform feature differences.
- **Recommend TypeScript gameplay through `deno_core`/V8 for the initial desktop product.** Rust handles engine systems; TS gives Islam and agents a fast authoring loop and mature debugging foundations. Console compatibility is a gating unknown.
- **React/TypeScript/Tauri v2 is the best editor fit**, conditional on an early native viewport experiment. Native window compositing, focus, DPI and overlays are substantial integration work.
- **Keep the schema source in Rust**, combining runtime reflection with explicit wire types and generated JSON Schema/TS. Stable asset/type identifiers and migrations belong to snengine.
- **Treat Rust hot-patching as an optional accelerator.** Asset/script reload and state-preserving restart must work first. Subsecond still has significant layout, workspace and thread-local restrictions.
- **The biggest risks are integration ownership, console ports, compilation and authoring tools.** Buy community leverage at subsystem boundaries; spend custom engineering on the product's differentiators.

Evidence checked **2026-10-22**. Versions below were queried from crates.io and GitHub release metadata, rather than inferred from training data. “Recommendation,” proposed timings and architecture choices are engineering judgments. No engines, reference clones or benchmarks were built/run; no console NDA material was available.

# Findings

## 1. Engine landscape and the Bevy decision

**Bevy 0.20.0 is the strongest reusable foundation.** Its current release includes BSN syntax improvements, editor-oriented Feathers widgets, mesh-shader work, WESL adoption and further Solari path-tracing improvements. These demonstrate serious momentum, not UE feature completeness. The release still lists `.bsn` files and a remote inspector among upcoming work. [Bevy 0.20 release](https://bevy.org/news/bevy-0-20/).

BSN's composable scene model and `bsn!` macro landed in **0.19**, June 19. Composable templates, patches and dependency-aware spawning are useful precedents for prefabs and UI. **Do not mistake the shipped Rust macro for a finished, editable, hot-reloadable disk format**: the 0.20 roadmap explicitly still calls for that format. Avoid making snengine's project format depend directly on unsettled BSN syntax. [Bevy 0.19 scenes](https://bevy.org/news/bevy-0-19/#next-generation-scenes), [0.19–0.20 migration](https://bevy.org/learn/migration-guides/0-19-to-0-20/).

Required components let a component declare other components that insertion should supply. They reduce bundle boilerplate and help establish valid runtime configurations; they do not replace authoring validation, asset dependency tracking or scene migrations. `bevy_reflect` supplies runtime field/type inspection, dynamic values, registered type data and reflection-based serialization, independently of Bevy's renderer. [Component API](https://docs.rs/bevy_ecs/latest/bevy_ecs/component/trait.Component.html), [reflection documentation](https://docs.rs/bevy_reflect/latest/bevy_reflect/).

The **Bevy Remote Protocol is real infrastructure**, using JSON-RPC 2.0 with ECS queries/mutations, watches and `registry.schema`. Its source includes JSON Schema/OpenRPC machinery. Community MCP integration exists: `bevy_brp_mcp` **0.23.0** depends on Bevy 0.20. This is useful prior art and a bootstrap tool, not an official guarantee of safe editor transactions. snengine still needs semantic operations, validation, undo, stable identifiers, capture and deterministic stepping. [Pinned BRP implementation](https://github.com/bevyengine/bevy/blob/v0.20.0/crates/bevy_remote/src/lib.rs), [BRP schemas](https://github.com/bevyengine/bevy/tree/v0.20.0/crates/bevy_remote/src/schemas), [community MCP project](https://github.com/natepiano/bevy_brp).

**Fyrox:** GitHub's latest named release is **1.0.0**; the published `fyrox` crate is **1.0.1**. It already offers a native scene/UI editor, animation tools and native game-code reload. Study its complete authoring loop and re-instancing rather than dismissing it as a renderer. Its own release notes acknowledge a small, underfunded team. Adopting the whole engine would also adopt its renderer, UI model and plugin architecture; rebuilding those around snengine's pillars reduces the attraction. [Fyrox 1.0](https://fyrox.rs/blog/post/fyrox-game-engine-1-0-0/), [crate version](https://crates.io/crates/fyrox).

**godot-rust/gdext:** **0.5.5**, August 9, remains maintained and exposes Godot 4 through GDExtension. This is a practical way to author Rust extensions inside an established editor. It does not make Godot's engine core Rust or provide a neutral foundation for snengine's rendering/editor architecture. Borrow its typed handle and foreign-object ownership lessons. [gdext release](https://github.com/godot-rust/gdext/releases/tag/v0.5.5), [project overview](https://godot-rust.github.io/).

Lessons from apparent casualties require precision:

- **Ambient is paused indefinitely**, with its team pointing to Braindump. The repository is not archived. Its Rust/Wasm/WebGPU/networked-runtime architecture is instructive, but not a maintained product dependency. The lesson is to avoid simultaneously inventing engine, deployment platform, package ecosystem and multiplayer semantics. [Ambient README](https://github.com/AmbientRun/Ambient).
- **kajiya is archived and explicitly unmaintained.** Its README describes a spare-time Rust/Vulkan GI experiment, not a shipping general-purpose renderer. It proves advanced rendering can be expressed in Rust; it does not supply production tooling or platform coverage. [kajiya](https://github.com/EmbarkStudios/kajiya).
- **Embark's old rust-gpu repository is archived; the community successor is active**, with **0.11.0 released October 13, 2026**. Do not generalize this into “Embark abandoned Rust”; public project status cannot establish its entire internal language strategy. [old repository](https://github.com/EmbarkStudios/rust-gpu), [community release](https://github.com/Rust-GPU/rust-gpu/releases/tag/v0.11.0).
- **Traverse's Breda is a current positive example**, not a verified dead project. Traverse describes ongoing Rust graphics work, neural operators and render-graph integration in Breda. Public evidence supports the technology's existence and continued use; I did not verify a public engine distribution, reusable source release or complete platform matrix. [Traverse](https://traverse.nl/), [Breda GPU workloads](https://traverse.nl/research/gpu-inference/).

**Recommendation: selected Bevy foundations.** A full fork inherits upstream migration work plus responsibility for every divergence. Starting ECS/reflection from scratch spends years on largely undifferentiated machinery. Keep all Bevy crates on one tested release; integrate directly internally, with narrow boundaries around persistent data and render extraction. Do not wrap every Bevy type merely to pretend independence. Use full Bevy/Solari as a comparison harness if helpful; do not make its current renderer the permanent architecture by accident.

## 2. GPU access, fidelity and shaders

**Current wgpu: 30.0.1**, August 22. Bevy 0.20's release-tagged manifest uses wgpu 30, so this is a compatible foundation, not a hypothetical future upgrade. Native APIs exceed the browser standard. [wgpu release](https://github.com/gfx-rs/wgpu/releases/tag/v30.0.1), [Bevy render manifest](https://github.com/bevyengine/bevy/blob/v0.20.0/crates/bevy_render/Cargo.toml).

The important capability distinctions are:

- **Bindless:** texture/buffer binding arrays, nonuniform indexing and partially bound arrays exist as native features, with differing backend support and limits. This is useful descriptor indexing, not a promise of universally unbounded resources or browser availability. [wgpu feature definitions](https://docs.rs/wgpu/30.0.1/wgpu/struct.Features.html).
- **Mesh/task shaders:** experimental support spans Vulkan, DX12 and Metal hardware paths. In the pinned source, Naga translation support is narrower; other paths may need shader passthrough. Capability support and shader-language translation are separate tests. [mesh extension](https://wgpu.rs/doc/wgpu/documentation/extensions/mesh_shading/), [v30 feature source](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-types/src/features.rs).
- **Ray tracing:** acceleration structures and experimental inline ray queries exist. There is a documentation discrepancy: the feature comment lists Vulkan, while the **same v30.0.1 Metal adapter source enables `EXPERIMENTAL_RAY_QUERY`** on supported hardware. Bevy 0.20 also reports Solari on Metal. Treat Vulkan and supported Metal as evidenced paths; I did not verify equivalent complete DX12 ray-query or ray-tracing-pipeline support. Inline queries are not the whole DXR/Vulkan ray-pipeline/SBT feature set. [Metal implementation](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-hal/src/metal/adapter.rs), [Solari release evidence](https://bevy.org/news/bevy-0-20/#solari-and-dlss).
- **Multi-queue/async compute:** explicit queue-family ownership and user-scheduled compute/copy queues are not a verified stable wgpu 30 capability. The native unsafe multi-queue RFC remains open. Parallel CPU command recording is different from simultaneous GPU queues. [multi-queue RFC](https://github.com/gfx-rs/wgpu/issues/8844).
- **Pipeline caches:** an explicit cache API exists, but v30 documentation/source says **Vulkan only**. Implement pipeline warmup and cache invalidation keyed by driver/device, shader and layout; do not promise persistent PSO caching on every backend. [PipelineCache](https://docs.rs/wgpu/30.0.1/wgpu/struct.PipelineCache.html).

**A wgpu-only contract can constrain access and optimization; it does not inherently cap visual quality.** UE-level fidelity requires streaming geometry/textures, GI, shadows, animation, VFX, authoring and profiling working together. A raw API grants control; it supplies none of those systems.

Recommended sequence: own a small renderer interface and render graph; implement the first Windows/Vulkan vertical slice with wgpu. Immediately exercise bindless materials, ray-query GI, indirect geometry and shader reload in a representative scene. If explicit multi-queue, ray pipelines, sparse resources, aliasing or vendor SDK integration is a measured blocker, add **one raw `ash` backend** before hardening public renderer contracts. Retain wgpu for portable targets. Do not build Vulkan, D3D12 and Metal backends concurrently in advance of need.

`ash` exposes Vulkan with substantial unsafe lifetime/synchronization responsibility. `windows` provides D3D12/COM access; `objc2-metal` is the modern Metal-binding candidate. Raw wgpu HAL interop can help a specific extension, but its tracking and ownership rules make “mix arbitrary raw commands into wgpu” a dangerous default. Native handles, fences and memory lifetimes need explicit ownership. [ash](https://github.com/ash-rs/ash), [windows-rs](https://github.com/microsoft/windows-rs), [objc2](https://github.com/madsmtm/objc2).

**Slang is the preferred high-end shader language.** Current compiler release: **2026.20**, October 17. It offers parameter reflection, interfaces/generics and native SPIR-V/DXIL paths suited to generated material graphs. Start with a pinned `slangc` worker and reflection JSON, caching cooked outputs; avoid embedding the compiler in every runtime. For in-process integration, the shader binding is **`shader-slang` 0.1.0**, from FloatyMonkey's `slang-rs` repository. The crates named `slang`/`slang-rs` are not interchangeable shader-compiler bindings. [Slang releases](https://github.com/shader-slang/slang/releases), [reflection API](https://shader-slang.org/blog/2024/12/18/reflection-api-doc-update/), [Rust bindings](https://github.com/FloatyMonkey/slang-rs).

Slang's own documentation still labels **Metal and WGSL support work in progress**. A single source language does not ensure every material translates everywhere. Maintain an explicit portable shader subset, WGSL/WESL support and conformance scenes. Naga is valuable validation/translation infrastructure; unsupported SPIR-V features cannot be assumed to survive its IR. rust-gpu's active revival is welcome, but SPIR-V focus and compiler coupling make it an R&D option rather than the default material language. [Slang target matrix](https://github.com/shader-slang/slang#target-support), [rust-gpu architecture](https://github.com/Rust-GPU/rust-gpu).

## 3. Reflection becomes an authoring and tool schema

**Use `bevy_reflect` for live runtime inspection**, with registered metadata for labels, ranges, units, defaults, read-only fields, asset filters and documentation. Its `'static`/`Send`/`Sync` requirements fit owned ECS data; borrowed runtime internals should remain unexposed. Reflection serializers are useful, but automatically reflected Rust type paths are not a durable project format. [reflection API](https://docs.rs/bevy_reflect/latest/bevy_reflect/).

**Use Serde + Schemars + ts-rs on explicitly exposed Rust types.** The same declaration can derive serialization, JSON Schema and TypeScript; this is one source of truth without requiring one universal derive. `schemars` respects relevant Serde shape attributes; `ts-rs` documents supported attributes and warns about unsupported ones. Specta is attractive for Tauri command/function exports, but current v2 remains **2.0.0-rc.27**, while its stable line is older. Pick ts-rs initially to avoid making an RC binding system foundational. [Schemars](https://schemars.com/), [ts-rs](https://github.com/Aleph-Alpha/ts-rs), [Specta](https://github.com/specta-rs/specta).

**Facet is a credible challenger**, not vaporware: **0.46.5 stable; 0.50.0-rc.7 prerelease** observed. Its derive drives serialization, inspection and structural tooling; the ecosystem lists `facet-json-schema` and `facet-typescript`. It better approximates a unified reflection ecosystem, but introduces another fast-changing foundation without Bevy's existing ECS integration. Prototype on one isolated document type; do not derive both complete reflection systems across the engine. [Facet overview](https://facet.rs/), [ecosystem](https://facet.rs/ecosystem/).

Recommended contract: persist UUID/string asset and entity identifiers, explicit stable type/field keys and document versions. Runtime `Entity` and `TypeId` stay process-local. Encode 64-bit IDs safely across JSON rather than silently rounding JavaScript numbers. Generated bindings expose handles and batched operations, never Rust pointers. JSON Schema describes representation; semantic validators enforce units, references and invariants. The inspector, scripts, CLI and MCP all invoke the same validated command path, producing undoable transactions. Snapshot generated schemas and representative round-trips to catch drift. Do not attempt arbitrary Rust-method binding generation in the first milestone.

## 4. Iteration speed and real hot reload

Keep changing gameplay out of the engine's heaviest generic crates. Use a modest workspace divided by responsibility, narrow dependencies, development codegen settings and optimized third-party dependencies. Windows should start with **stable Rust + `rust-lld`**, measured against the existing linker. Bevy's `dynamic_linking` cuts relinking, but is a development arrangement, **not gameplay reload**; Windows also has an exported-symbol caveat. [Bevy setup](https://bevy.org/learn/quick-start/getting-started/setup/).

Cranelift's current repository distributes nightly components for Linux, macOS and x86_64 Windows. That is newer than documentation implying Windows always needs manual builds. However, SIMD coverage and panic unwinding have limitations; **unwinding is not supported on Windows/macOS in its documented configuration**. Do not blindly combine it with hot-patch machinery relying on caught unwinds. Keep LLVM as the correctness/shipping baseline and Cranelift opt-in. Mold is a Linux option, not a Windows recommendation. [Cranelift README](https://github.com/rust-lang/rustc_codegen_cranelift).

`sccache` is useful for shared CI/dependency builds, but incrementally compiled crates cannot be cached, and linker-invoking targets have exclusions. Disabling incremental everywhere to “enable caching” can worsen local iteration. Keep local incremental and separate cache-oriented CI profiles; measure actual cache hits. [sccache caveats](https://github.com/mozilla/sccache#rust).

**Subsecond 0.7.10** offers function detours and ThinLink, but its documentation still says experimental and currently patches only the tip binary crate. Struct layout changes require re-instancing; static initializers do not rerun, destructors have restrictions, and tip-crate thread locals can reset or crash complex configurations. Its advertised sub-500 ms incremental build is an upstream claim, not a snengine measurement. Bevy integration reduces integration work, not these fundamental state-layout questions. [Subsecond documentation](https://docs.rs/subsecond/latest/subsecond/).

Conventional dylib reload is also possible: version a C ABI, keep ownership in the host, stop jobs/callbacks before replacement and migrate serialized state. Rust does not offer a stable Rust ABI; old trait objects, function pointers and allocations must not outlive their code. Windows DLL locking commonly requires generation-named copies. Prefer process restart plus restored world state over elaborate unsafe reload when the first approach meets the latency budget. [Rust FFI guidance](https://doc.rust-lang.org/nomicon/ffi.html).

**Proposed warm-cache budgets, not benchmarks:** simple asset/UI edits **50–300 ms**; TS transpile/module replacement **100 ms–1 s**; a small Rust leaf edit **1–5 s**; broader engine edits **5–30+ s**; cold/native dependency rebuilds **minutes**. Shader compilation and large texture cooking can exceed those budgets independently. Record save-to-first-correct-frame p50/p95 on Islam's machine, including state restoration. Assets, shaders and scripts must reload independently of Rust compilation, retaining the last valid version on error.

## 5. Gameplay scripting on the Rust core

**Recommend TypeScript compiled to JS, hosted with `deno_core`/V8 for Windows-first development.** `deno_core` **0.413.0** provides embedded JS, native operations, modules, inspector integration and source-map facilities. It does **not** automatically provide TypeScript transpilation or the whole Deno/Node environment. Build a small engine SDK and deterministic host scheduler, not an embedded general-purpose OS runtime. Cache transpilation and surface TS diagnostics without blocking the renderer. [deno_core runtime](https://docs.rs/deno_core/latest/deno_core/struct.JsRuntime.html), [scope of the core crate](https://github.com/denoland/deno_core/tree/main/core).

Why this choice: existing TS skills, agent familiarity, reusable generated types and an established debugger protocol. Rust remains available for expensive systems. Use one scene/game scripting realm initially, batched component reads/writes, owned snapshots and generation-checked handles. Avoid a JS-to-Rust call per component per entity. Keep authoritative script state explicit and serializable; replace modules at tick boundaries with migrations and cancellation of old callbacks. V8 inspector support is a foundation for debugger tooling, not a debugger UI already delivered by the crate.

Alternatives have real advantages:

- **Rust gameplay + Subsecond:** maximal native reuse and safety for compiled code, but compilation, re-instancing and extension lifetime rules remain. Offer later as an advanced path, rather than requiring beginners to solve ECS borrowing to move a character.
- **`rquickjs` 0.14.0 / QuickJS-NG:** much smaller interpreter with module support, memory/stack limits and interrupt hooks. A strong choice when JIT-free deployment and footprint dominate. It lacks the same verified V8-inspector tooling path; benchmark game workloads before choosing it for thousands of scripts. [rquickjs](https://github.com/DelSkayn/rquickjs), [runtime controls](https://docs.rs/rquickjs/latest/rquickjs/struct.Runtime.html).
- **Boa 0.22.0:** embeddable pure-Rust JS avoids the V8 C++ distribution chain. I did not verify comparable debugger integration or game workload performance; neither “pure Rust” nor conformance claims establish those. [Boa](https://github.com/boa-dev/boa).
- **Luau via `mlua` 0.12.2:** excellent game-oriented alternative with static type checking tooling and sandbox support. Binding metadata could generate Luau definitions. It adds another authoring language for Islam; keep it the principal fallback if certified-platform/JIT constraints invalidate V8. Type checking is not automatically performed by executing a Luau VM. [mlua](https://github.com/mlua-rs/mlua), [Luau embedding/sandbox controls](https://luau.org/api/).
- **Hosted C#:** feasible through `nethost`/`hostfxr` and a native function boundary. .NET hosting, GC roots, assembly reload, deployment and restricted-platform AOT add another substantial runtime integration. Unity familiarity does not make that integration free. [Microsoft native-host guide](https://learn.microsoft.com/en-us/dotnet/core/tutorials/netcore-hosting).
- **Wasmtime 50.0.0:** valuable for untrusted plugins/mods needing Wasm isolation, explicit imports and fuel/epoch budgets. Its AOT and interpreter options do not automatically guarantee console certification. It is a deployment/isolation mechanism, not an ergonomic gameplay language or automatic way to run arbitrary TS. [Wasmtime execution controls](https://docs.wasmtime.dev/api/wasmtime/struct.Config.html), [platform modes](https://docs.wasmtime.dev/stability-platform-support.html).

V8 is a heavy C++ dependency with frequent upstream updates. Rusty V8 normally downloads prebuilt static libraries; unusual targets may require expensive custom builds. iOS jitless support exists, but that is not proof of production suitability on every restricted platform. Budget memory/GC and execution termination; expose only approved host capabilities. Do not call same-process scripts a strong boundary for hostile native plugins. [rusty_v8 distribution and platform notes](https://github.com/denoland/rusty_v8).

## 6. Editor technology and native viewport integration

**Tauri v2 + React/TS is the recommended shell**, because sophisticated panels, forms, command search and agent-readable DOM can reuse Islam's strongest ecosystem. Current Rust crate: **2.12.5**. Keep scene state authoritative in Rust and exchange commands/deltas, rather than serializing the entire ECS into React each frame. [Tauri](https://v2.tauri.app/), [current crate](https://crates.io/crates/tauri).

There are three distinct viewport strategies:

1. **Native child/sibling surface:** allocate a rectangular native viewport alongside webview panels. On Windows that means HWND placement/clipping and a native swapchain. This is the first docked integration to prove; a separate top-level viewport is an acceptable initial fallback. Coordinate DPI, focus, mouse capture, IME, resize, pop-out windows and accessibility. HTML popovers cannot be assumed to overlay a separate native surface. Tauri's event loop must remain authoritative; do not start a competing default Bevy/winit runner.
2. **Shared GPU resources/native compositor:** Windows DirectComposition can combine native visuals and WebView2's composition tree. This is potentially efficient but platform-specific; it is **not** a portable Tauri API for importing a Rust texture into a DOM/WebGPU canvas. Ownership, adapter compatibility, fences, alpha/color space and input routing are required. macOS/Linux need different implementations. [WebView2 composition APIs](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/overview-features-apis#rendering-webview2-using-composition).
3. **Streaming into the webview:** easiest transport abstraction for remote editing, but raw readback/copy costs or encoded video latency hurt manipulation. Raw 1920×1080 RGBA at 60 Hz is about **0.50 GB/s** before overhead. Useful for thumbnails/remote sessions; avoid it as the default local high-fidelity viewport.

Wry has an actual **wgpu + transparent child webview example**, which proves coexistence, not arbitrary production docking. A historical Windows 11 transparency bug in that example is closed; Linux's official graphics troubleshooting still documents WebKitGTK/driver/Wayland failures. Validate target machines rather than presenting old issues as universal current blockers. [Wry example](https://github.com/tauri-apps/wry/blob/dev/examples/wgpu.rs), [Windows issue](https://github.com/tauri-apps/wry/issues/1212), [Linux issues](https://v2.tauri.app/develop/debug/linux-graphics/).

**Alternatives:** egui **0.37.0** is the lowest-risk native tooling/debug UI, with wgpu integration and AccessKit; polished editor interactions still require design work. A Bevy-native editor shares render/input machinery, but Feathers and the upstream editor remain evolving foundations. GPUI **0.2.2** is a serious option with Zed production experience, Windows support and Apache-2.0 licensing for GPUI itself; its pre-1.0 API, Rust UI learning curve and viewport integration still cost time. Dioxus **0.7.10** is appealing for React-like Rust and hot reload, but its native Blitz route remains beta. Slint **1.18.1** provides declarative native UI and tooling, with licensing terms that deserve an explicit engine-distribution check. Xilem/Masonry **0.4.0** remain explicitly experimental. [egui](https://github.com/emilk/egui), [GPUI README](https://github.com/zed-industries/zed/tree/main/crates/gpui), [Dioxus rendering models](https://dioxuslabs.com/learn/0.7/beyond/project_structure/), [Slint](https://github.com/slint-ui/slint), [Xilem](https://github.com/linebender/xilem).

For agents, combine DOM/accessibility locators with semantic engine commands and renderer-owned captures. A browser screenshot may omit the native viewport. Tauri's current WebdriverIO integration supports an embedded driver across desktop platforms; native `tauri-driver` alone remains Windows/Linux. This is more current than claiming macOS Tauri automation is categorically unavailable. [Tauri WebDriver](https://v2.tauri.app/develop/tests/webdriver/).

## 7. Native runtime game UI

**HTML/CSS/Tailwind-like authoring is feasible without shipping a browser.** Taffy **0.15.0** supplies Flexbox/Grid/Block layout, not selectors, painting, text or an event system. Parley **0.12.0** supplies advanced text layout; cosmic-text **0.19.0** is an alternative integrated shaping/layout/editing stack. Vello **0.11.0** supplies GPU vector rendering. None alone is a complete game UI toolkit. [Taffy](https://docs.rs/taffy/latest/taffy/), [Parley](https://github.com/linebender/parley), [cosmic-text](https://github.com/pop-os/cosmic-text), [Vello](https://github.com/linebender/vello).

Blitz combines Stylo CSS resolution, Taffy layout, Parley text and modular painting; it has a wgpu texture example and a beta status. Current `blitz-dom`: **0.2.4 stable; 0.3.0-beta.4 prerelease**. Its README explicitly says JavaScript/Python bindings are not provided. Dioxus Native is a Rust frontend to this stack, not a drop-in way to execute React DOM components. [Blitz architecture/status](https://github.com/DioxusLabs/blitz).

Recommendation: start with a constrained retained UI document, Taffy + Parley, and an engine renderer integration. Support utility classes/design tokens, flex/grid, images, text, clipping, transforms and explicit events. Compile utility classes to supported native properties; actual Tailwind output can include unsupported CSS and cannot be advertised wholesale. React/TSX can be an authoring compiler frontend later; it need not be the runtime reconciler. Keep controller focus, localization, Arabic/bidi, font fallback, IME, hit testing and semantic IDs first-class. Evaluate Blitz as the implementation if broader CSS fidelity is required, rather than gradually rebuilding a browser. `bevy_ui` is a useful quicker alternative if the project accepts its ECS/renderer coupling and styling model.

## 8. Remaining engine subsystems

**Physics:** default to **Rapier 0.36.1**, independently of the renderer. It offers Rust-native 2D/3D physics, SIMD and optional parallel stepping. **Avian 0.8.0 supports Bevy 0.20** and keeps physics in the ECS, which is attractive if accepting that tighter coupling. Jolt remains valuable for established game features, but bindings vary sharply: `rolt`/`joltc-sys` releases still target Jolt 5.0, while newer **oxijolt 1.2.0 targets Jolt 5.6** and has a smaller track record. Compare character controllers, joints, stacks and rollback on the intended game before swapping. Do not infer determinism from the implementation language. [Rapier](https://github.com/dimforge/rapier), [Avian compatibility](https://github.com/avianphysics/avian), [Jolt bindings](https://github.com/SecondHalfGames/jolt-rust), [oxijolt](https://github.com/pockerhead/oxijolt).

**Audio:** **Kira 0.12.5** is a practical starting point for spatial audio, mixing, effects and timed/tweened parameters. **Firewheel 0.14.0** offers a graph-oriented lower layer; its README describes planned upstreaming into Bevy, not completed universal integration. **oddio 0.7.4** offers compact spatial audio but its published release is from 2023. FMOD/Wwise can be integrated through vendor APIs/FFI when professional authoring, codecs or platform support justify the cost; Rust wrapper existence does not establish vendor support or license coverage. [Kira](https://docs.rs/kira/latest/kira/), [Firewheel](https://github.com/BillyDM/firewheel), [oddio](https://github.com/Ralith/oddio).

**Assets:** `gltf` **1.4.1** is a glTF 2.0 importer, with extension coverage requiring review. Use `ufbx` **0.11.5** for FBX conversion and `meshopt` **0.7.0** for mesh optimization/compression. They wrap native code. Cook runtime data with content hashes and importer versions, outside the game process. `ktx2` **0.5.0** reads the container; it is not itself the universal texture encoder/transcoder. `basis-universal` **0.3.1** is an older Rust binding, so audit its bundled native library rather than assuming current Basis features. [gltf](https://github.com/gltf-rs/gltf), [ufbx](https://github.com/ufbx/ufbx-rust), [meshopt](https://github.com/gwihlidal/meshopt-rs), [ktx2](https://crates.io/crates/ktx2), [Basis binding](https://github.com/aclysma/basis-universal-rs).

**Animation/navigation:** reuse Bevy animation for a prototype, but expect custom authoring, retargeting, root-motion and graph work. `ozz-animation-rs` **0.11.0** reimplements Ozz's runtime in Rust while relying on the C++ offline tools; it is not a full animation editor. For navigation, Recast/Detour is a mature FFI option; `recastnavigation-sys` **1.0.3** is an older wrapper requiring coverage review. Pure-Rust `landmass` **0.9.3** handles navigation/avoidance, but does not erase mesh-generation needs. `oxidized_navigation` **0.12.0** is an older Bevy-linked candidate, not an assumed 0.20-compatible choice. [Ozz port](https://github.com/SlimeYummy/ozz-animation-rs), [Recast](https://github.com/recastnavigation/recastnavigation), [Landmass](https://github.com/andriyDev/landmass).

**Profiling/networking:** use `tracy-client` **0.19.0**, GPU timestamps/capture tools and structured `tracing`; Puffin **0.20.0** is a lighter in-engine alternative. CPU instrumentation alone does not profile GPU execution. Quinn **0.11.12** supplies QUIC transport, not replication or prediction. Lightyear **0.31.0** targets Bevy 0.20 and now builds world replication on Replicon, rather than requiring a simplistic either/or decision. Replicon is **0.45.2**. Defer game-specific rollback, authority and transport choices until the first game's needs are known. [Tracy](https://github.com/nagisa/rust_tracy_client), [Puffin](https://github.com/EmbarkStudios/puffin), [Quinn](https://github.com/quinn-rs/quinn), [Lightyear](https://github.com/cBournhonesque/lightyear), [Replicon](https://github.com/simgine/bevy_replicon).

FFI remains normal engineering: pin native revisions, provide reproducible per-target artifacts, document alloc/free ownership and callback threads, isolate unsafe code in small adapters, and translate errors/panics at ABI boundaries. CMake/SDK/CRT mismatches and missing target binaries can dominate setup despite an otherwise Rust-native core. Prefer native importers/compiler workers out of process and keep the shipped runtime dependency graph smaller.

## 9. Platforms

Windows/Linux/macOS are the credible initial product set. Android/iOS have official Rust targets; wgpu has Vulkan/Metal paths. Mobile still requires lifecycle, surface recreation, thermal budgets, touch, audio interruptions and packaging work. Editor technology does not need to ship with games. [Rust platform support](https://doc.rust-lang.org/rustc/platform-support.html), [wgpu platform coverage](https://github.com/gfx-rs/wgpu).

**Switch 2, PS5 and Xbox: commercial support not publicly verified.** Public Rust targets include a freestanding original Switch target; that is not proof of a licensed Switch 2 SDK, certification or middleware integration. No public first-class PS5/Xbox Rust toolchain/backend combination was verified here. Private ports may exist; neither that possibility nor an open Bevy console-support issue is a product commitment. Obtain licensed SDK access or a porting partner, then prove rendering, audio, threading, allocation, scripting and packaging on each target. Console/JIT/AOT constraints can change the scripting choice. [official target list](https://doc.rust-lang.org/rustc/platform-support.html), [Bevy console tracking](https://github.com/bevyengine/bevy/issues/8161).

Web is a **bonus capability tier**: Rust/Wasm + WebGPU, lower memory budgets and portable shaders. Native mesh/ray/bindless extensions do not automatically reach browsers. Native embedded V8 is not the browser build's scripting VM; browser JS can consume the same generated SDK, with an explicit integration adapter. Shared-memory/threading deployments have additional browser constraints. Do not make flagship fidelity depend on web feature parity.

## 10. Keeping AI agents productive in Rust

Engineering judgment, not a comparative agent benchmark: agents benefit from compiler-checked refactors, explicit enums and narrow APIs. They struggle with cyclic ownership, sprawling generics, async borrows, macros hiding control flow and obsolete ecosystem examples. Compile latency turns an ordinary correction loop into a productivity problem.

Use concrete owned domain types, typed/generational handles and short-lived ECS borrows. Move expensive work to tasks with owned input/output and apply results at clear tick boundaries. Keep async I/O at subsystem edges; never hold a mutable world borrow across an await. Avoid solving borrow errors with pervasive `Arc<Mutex<_>>`, unsafe code or lifetime-heavy public APIs. Dynamic dispatch at coarse boundaries is often simpler; profile inner loops before choosing more generic machinery.

Give agents a small runnable example per subsystem, pinned dependency versions and an `AGENTS.md` listing crate ownership, thread/unsafe invariants and exact checks. Default loop: `cargo check -p changed_crate`, focused Clippy, then focused nextest tests. Reserve workspace/all-feature/platform matrices for CI. Suggested lints: workspace `clippy::all`, documented unsafe blocks, unsafe operations explicitly marked, and no unwrap/expect in production paths except documented invariants. Avoid globally denying every pedantic lint.

Use nextest **0.9.149** for execution and Insta **1.49.0** for reviewed schema/command/document snapshots. Add behavioral integration tests for save/load migrations, undo and script reload, plus a small deterministic render capture suite with tolerances. Do not replace assertions with enormous opaque snapshots. [nextest project](https://github.com/nextest-rs/nextest), [Insta](https://insta.rs/docs/).

# Where Rust hurts + mitigations

1. **Compile/agent feedback latency.** Keep gameplay/assets reloadable, split by actual dependency boundaries, use scoped checks, cache CI artifacts and measure p95 iteration. Do not make nightly codegen a prerequisite for contributors.
2. **Mutable interconnected worlds.** Model relations through handles, use short ECS queries/command buffers and clear ownership phases. Keep borrowed views local instead of propagating lifetimes through the whole engine API.
3. **Hot reload and ABI stability.** Persist state independently of code, version contracts, re-instance changed types, cancel old tasks and retain restart/restore as the reliable fallback. Add Subsecond only where its restrictions are satisfied.
4. **High-end rendering/platform gaps.** Establish a representative GPU capability test early. Own shader/renderer boundaries and add a single raw backend only against concrete blockers. Pin GPU dependencies together.
5. **Console support.** This is a release-planning risk, not a Cargo feature. Obtain SDK/partner evidence before advertising a target; gate V8 and middleware decisions on that evidence.
6. **Editor/UI integration.** Prove multi-monitor DPI, docking, focus, overlays and captures before committing months to Tauri panels. If native compositing cannot meet the interaction bar, choose egui/GPUI with the same command/document backend.
7. **Ecosystem churn and native dependencies.** Maintain a tested lockfile and upgrade window; isolate FFI, keep importers out of process and avoid adopting multiple experimental foundations simultaneously.
8. **Authoring completeness.** Rust crates supply mechanisms. Prefabs, migrations, material/VFX graphs, animation tools, UI widgets and diagnostics remain product engineering. Ship one small game/editor workflow end to end before adding more subsystems.

# Open questions

- Are consoles a launch requirement or a later funded port? This decides whether V8 can be selected before licensed-platform validation.
- What is the minimum flagship GPU and target frame budget? Define a representative scene and compare wgpu against the first measured native-backend blocker.
- Must editor HTML controls overlay the 3D viewport arbitrarily? If yes, child-window embedding may be insufficient; native compositor work becomes an early requirement.
- Is “HTML/CSS-like game UI” a constrained engine format, or actual browser-compatible documents? The latter favors Blitz and a much larger compatibility obligation.
- What world/state must survive gameplay reload, and what p95 interruption is acceptable? Measure TS reload and restart/restore before investing in universal Rust patching.
- Which first game proves animation, physics and networking requirements? Avoid selecting advanced middleware or deterministic rollback without that workload.

**Final recommendation:** build on Bevy's maintained foundational crates without forking, own snengine's authoring contracts and renderer, use TypeScript for the default gameplay loop, and make the Tauri viewport and high-end GPU experiments the first architecture gates. Treat console enablement, iteration latency and tool completeness as the top delivery risks, with the concrete mitigations above.
